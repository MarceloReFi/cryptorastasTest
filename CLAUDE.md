Repo Instructions — Marcelo Silva
Apply these standards to this repo. If this is an existing repo, audit it against every point below and report findings before making changes. If this is a new repo, apply from the first commit.
Hygiene

* Repo description (GitHub settings, not just README) must be filled in, one line, accurate.
* README must state status clearly: what this is, what stage it's at (pre-launch / active development / production). Never leave a repo undescribed or looking abandoned.
* If this repo is a fork: only keep it if there are original commits building on top of it. A fork with zero original commits should not exist under this account — flag it for deletion instead of leaving it.

Attribution

* Any collaborator credited in this repo must be credited for their specific contribution (e.g. "UI design," "compliance structure"), never vague "team effort" language.
* Before crediting anyone, confirm with Marcelo whether this repo is sole-IP/ownership for legal or business reasons. If so, do not add contributor credit regardless of who wrote code, unless Marcelo explicitly approves it for this repo.
* Describe Marcelo's own role precisely — "developer" vs. "research lead" vs. "security auditor" are not interchangeable. Never let a README imply a role he didn't have.
* Never publish a claim, link, or contributor credit that hasn't been verified. If unconfirmed, ask rather than assume.

Commits & branches

* No AI-tool self-promotion anywhere: no session links, no "Generated by X" footers, no tool-specific branch name prefixes (e.g. `claude/...`). Use plain, descriptive branch names instead.
* Commit messages describe what changed and why — never what tool made the change.
* Delete branches once merged. Don't let stale branches accumulate.

Code architecture

* DRY: no duplicated logic — extract shared code into functions/modules.
* KISS: implement the simplest solution that works; add complexity only when the simple version demonstrably fails.
* YAGNI: build only what's needed now — no speculative abstractions or unused feature scaffolding.
* Feature-based folders: organize by feature (`/login`, `/dashboard`, `/payments`), not by layer (`/components`, `/utils`) mixing unrelated features.
* Separation of concerns: business logic, UI, and data access live in separate files/functions, never tangled together.

Verification

* Never report a task as done without checking the actual file/repo state directly after the change. Print or confirm the final state.
* After any bulk/automated change, spot-check a sample before calling it closed.
* Do not take actions with side effects (creating forks, new repos, new files) beyond exactly what was asked. If something extra seems necessary, ask first.

Consistency

* Nothing in this repo should contradict Marcelo's CV, personal site (marcelorefi.github.io), or LinkedIn. If a discrepancy is found, flag it rather than silently resolving it either direction.
